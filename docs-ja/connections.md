# 接続と探索

接続ファイルは、アプリが呼び出してよいモデルの一覧です。このページでは、どのファイルが信頼されるか、SDK と CLI がそれをどう見つけるかを説明します。

## 接続ファイル { #the-connection-file }

TOML の形式は、モデルごとに一つの `[models.NAME]` セクションです（[アプリで判断を動かす](app.md#your-first-decision)の例を参照）。プロジェクトの `s1flow.toml` からコピーします。`default`（`--models` を付けないときに `s1flow run` と `doctor` が使うモデル）は任意で、アプリのファイルでは省けます。接続は、アプリが実装した独自の提供元を指すこともできます。

渡したファイル全体が、許されたモデルの集まりです。関係のない認証情報だらけの研究用カタログではなく、本番には専用のファイルを用意してください。ポリシーが、提供元の import、エンドポイントの URL、認証情報の名前や値を持ち込むことはできません。s1flow がプロジェクトのカタログをアプリのファイルに混ぜることもありません。

## SDK { #the-sdk }

`Client()` と `AsyncClient()` は、プロジェクトや設定ファイル、`.env`、組み込みのカタログを探しません。設定したモデルが必要とするときは、提供元が自分の API キーの環境変数を読みます。

直接の呼び出しで `"triage"` のような別名でモデルを指すときは、`connections=` を渡します。直接渡した `ModelSpec` や `DecisionModel` はすでに明示的なので、接続ファイルは要りません。接続は `client.connections` で参照できます。

`connections`、キャッシュ、ログの相対パスは、クライアントやポリシーを作ったときの作業ディレクトリを基準に解決します。SDK が dotenv ファイルを読むことはありません。`policies.load` には、明示的な `path=` か `root=` が要ります。今のプロジェクトからポリシーを探すことはなく、明示したポリシーのパスは `load` を呼んだときに解決します。

`cache_dir` は任意で、`Client` と `AsyncClient` にだけ効きます。提供元は、価格表のような補助的なデータに使います。s1flow が、実行時にモデルの答えを使い回すためにこれを使うことはありません。評価には専用の答えのキャッシュがあります。接続ファイルを読んでも何も作りません。提供元を作ったり確かめたりするには、`client.connections.build()` か `.check()` を使います。

## CLI { #the-cli }

コマンドが `--project PATH` と `--connections PATH` を取るかどうかは、`s1flow COMMAND --help` に出ます。

`--project` は、`s1flow.toml` を含むディレクトリか、`s1flow/s1flow.toml` を含むリポジトリを、ちょうど指していなければなりません。上の階層を探すことはありません。`--project` が無ければ、CLI は今のディレクトリから一番近い Git のルートまで上に向かって探します。Git リポジトリの外では、今のディレクトリと `./s1flow` だけを確かめるので、もっと深い場所から動かすときは `--project` を使ってください。

評価のコマンドは、`--connections` があればそれを、無ければ選んだプロジェクトの `s1flow.toml` を使います。`decide --policy`、`doctor --policy`、`adopt --spec --root` には明示的な `--connections` が要ります。`feedback record` はモデルを呼ばないので、取りません。

CLI は、プロジェクトのディレクトリ（プロジェクトが無ければ今のディレクトリ）と、その上から Git のルートまでのすべてのディレクトリの `.env` を、近い順に読みます。すでに設定されている変数が優先されます。プロジェクトが見つからないときは、エラーがどこから探し始め、どこを見たかを伝え、`--project PATH` か `--connections PATH` を勧めます。
