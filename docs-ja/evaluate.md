# 評価して比べる

アプリが動かすのと同じポリシーを自分のラベル付きケースで測り、モデルとプロンプトを比べ、どれを選んだかを記録します。コーディングエージェントは s1flow の Skill を通してこれをすべて行えます。このページは、その裏にあるリファレンスです。

## 評価用のツールを入れる { #install-the-evaluation-tools }

これらは本番のイメージではなく、開発環境に入れます。

| エクストラ | 追加されるもの |
|---|---|
| `eval` | 評価・比較・レポートのための numpy、scipy、scikit-learn |
| `llm` | LLM と比べるための LiteLLM |
| `optimize` | `eval` と `llm` に加えて、プロンプト最適化のための GEPA（実験的） |
| `images` | 画像を準備するための Pillow |
| `otel` | 任意のトレース用スパンのための OpenTelemetry API |

```bash
uv tool install "s1flow[eval]"
```

## コマンド { #the-commands }

```bash
s1flow init --task ticket-bug
# Fill in tasks/ticket-bug/task.py and add labeled data in the generated s1flow/ project.
s1flow cases check ticket-bug
s1flow run ticket-bug
s1flow report ticket-bug
s1flow adopt ticket-bug MODEL --reason "why this candidate" --json   # the new version is current
# open a pull request with the change: merging releases it
```

タスクで最初に `s1flow run` を実行すると、テスト用の割合をホールドアウトして `tasks/<task>/split.json` を書きます。`adopt` と `optimize` はこのファイルを読み、無ければ動かないので、`task.py` と一緒にコミットしてください。このファイルを書くコマンドはほかにありません。後から足したケースは ID のハッシュで振り分けられるので、ファイルは変わりません。テスト用にホールドアウトするほどラベル付きケースが無いときも、`run` はモデルに聞き、後の実行でファイルを書きます。

`s1flow init` は `s1flow/` プロジェクトを作るだけで、ほかには何もしません。`--skill` を付けると Agent Skill も書きます（[はじめる](get-started.md#add-the-skill-to-your-coding-agent)のとおり、プラグインとして入れることもできます）。プロジェクトのラインナップは 4 つの Decision Model を比べ、どれも `OPENROUTER_API_KEY` という一つのキーで動きます（issue くらいの大きさの入力で、1,000 回あたり $0.01〜$0.05）。ケースは GitHub の issue、アプリのログ、手元のラベルから集められます。GitHub からケースを取ってくる（Skill の `scripts/github.py`）には、`gh` CLI を入れてサインインしておく必要があります。

`Task` は評価を定義します。データ、ラベルの読み方、問い、objective、制約、ケースの分け方です。入力の準備にはアプリ自身の関数を使い回すか、アプリが実際に送った入力を再生してください。`task.py` はアプリと一緒にデプロイしません。評価と本番の実行は、問いの型、答えの検証、判断のルールを共有します。指標と最適化は評価だけのものです。

## 候補を比べる { #compare-candidates }

`s1flow report` は、開発用のケースだけを使って、すべてのモデルと問いのバリアントを並べて見せます。バリアントは問いの別の言い回しで、task.py に `variants={"strict": Boolean(instructions="...")}` のように書き、`model/strict` として動かします。`s1flow optimize` も同じ形でバリアントを足します。ターミナルには、タスクの objective の順に候補が並び、区別できない上位の候補には `=` が付きます（task.py の `tiebreak` の順、無ければ名前順）。どれを選ぶかの印は付けません。`--json` を付けると、同じ候補 ID と数値で各候補のすべての指標が出るので、人や、人の代わりに動くエージェントが、自分の基準で選べます。テスト用のケースでの最終結果は、候補を採用したときにだけ出ます。

`adopt --reason` は選んだ理由を記録し、作業ツリーでその候補を現在のものにします。それを含むプルリクエストがマージされると本番に入ります（[ポリシー、証拠、リリース](policies.md)を参照）。

`s1flow report ticket-bug --out DIR` は `DIR/comparison.json` を保存します。グラフ用のデータを含む、開発用の結果の完全なスナップショットです。問いのバリアントごとに `DIR/questions/<variant>.md` と `.json` も保存します。`s1flow report --from DIR/comparison.json` は、そのスナップショットを採点や確認をし直さずにオフラインで読みます。スナップショットには、出どころと日付、提供元とモデル、宣言した並列数と記録された並列数、レイテンシと費用の数字の出どころ（請求額、定価、あるいは推定・混在・不明と表示）が残ります。不明な値は不明のままです。テキストと JSON のどちらの出力も、`--limit`、`--offset`、完全一致の `--candidate model[:version][/variant]` で絞り込めます。

## グラフ { #charts }

結果をブラウザで見るには、同梱のレンダラーでローカルのページを作ります。標準ライブラリだけで動きます。

```bash
python <skill>/scripts/charts.py comparison.json --out comparison.html
```

保存したスナップショットだけを読むので、評価用のツールを読み込むことも、モデルを呼ぶことも、採点し直すことも、採用することもありません。ページは、比べたすべての候補の表から始まります。列は、タスク自身の objective、問いの型が持つ指標（適合率・再現率・F1、macro-F1、MAE と QWK、mean IoU、正解率）、API の費用、p90 レイテンシです。スナップショットにあるそのほかの指標も、クリック一つで出せます。各セルには最悪の値から最良の値までのバーがあり、列ごとの最良の値が強調され、列の見出しでその列の順に並び替わります。◆ は、表示中のすべての指標でこの候補と同等以上の候補がほかに無いものに付きます。重み付けも、どれを選ぶかの印もなく、比べる価値のあるものを示すだけです。表の下には、任意の 2 つの指標を取ったトレードオフのグラフがあります。比べなかった候補とその理由、確率の曲線、測り方の詳細は折りたたんであります。グラフは、出どころとサンプルの数を付けて SVG か PNG で書き出せます。

スコアの問い（0 から L-1 までの段階）は、期待される段階で読み、共通の指標に加えて MAE（既定の objective）と QWK で測ります。ボックスの問いは、共通の指標と、確信度で絞り込んだときの曲線を持ちます。はい／いいえの問いには、適合率・再現率と、キャリブレーションのグラフが加わります。選択の問いでは、モデルが本当の分布を返すとき、選ばれた答えの確率の曲線が出ます。提供元が独自に返す確信度は別の信号として扱い、曲線に必要な信号が無いときは確率の曲線を描きません。

## しきい値と区間 { #thresholds-and-intervals }

はい／いいえの問い（と、正の選択肢がある選択の問い）では、ルールを決める objective（Accuracy、F1、ExpectedLoss、Recall、Loss、または `sets=` で指定する独自の指標）が、開発用の各フォールドの学習側でしきい値を選びます。レポートは 3 つを分けて保ちます。そのままの指標、しきい値を合わせた交差検証の指標、ホールドアウトしたケースでの最終結果です。しきい値を合わせることは、確率をキャリブレーションすることとは違います。区間が重なる候補は、慎重な側に倒して一つのグループにまとめます。それは、実用上も統計上も、それらが同等だと証明するものではありません。不明な測定値が、設定した費用やレイテンシの上限を満たしたと数えられることはありません。

順位付けは、すべてのケースに答えがある候補だけを並べます。JSON の `candidates` には、根拠が違うものや不完全なものも残り、それぞれ何が足りないかが書かれます。

## 古い結果が使えなくなるとき { #when-old-results-stop-counting }

結果を使い回す前に、s1flow は実際に送った入力、問い、実際に使った接続、モデル ID、実装を確かめます。同じケース ID のまま入力を変えたり、エンドポイントやオプションを変えたりすると、前の応答は使い回されません。入力が変わっていなければ、モデルに聞き直さずにラベルを直せますが、それまでの評価結果とは合わなくなります。

並列数を変えると、それまでの性能の数字も使えなくなります。答えそのものは使い回せますが、古い時間を新しい並列数で測ったかのようには出しません。測り直すには `run --fresh` を使います。

評価で使う独自の提供元は、信頼された ModelSpec か TOML のエントリに `provider_revision` を書き、あなたの実装のコミットかパッケージのバージョンを示す必要があります。評価していない Client やポリシーには要りません。リビジョンを正しく保つのはあなたの責任です。署名ではなく、リモートのモデルの重みについては何も証明しません。
