# 評価して比べる

アプリが動かすのと同じポリシーを自分のラベル付きケースで測り、モデルとプロンプトを比べ、どれを選んだかを記録します。コーディングエージェントは s1flow の Skill を通してこれをすべて行えます。このページはエージェントが裏で使うコマンドのリファレンスです。

## 評価用のツールを入れる { #install-the-evaluation-tools }

評価用のツールは本番のイメージではなく開発環境に入れます。

| エクストラ | 追加されるもの |
|---|---|
| `eval` | 評価・比較・レポートのための numpy、scipy、scikit-learn |
| `llm` | LLM と比べるための LiteLLM |
| `images` | 画像を準備するための Pillow |
| `otel` | トレースのスパンを出す（任意）ための OpenTelemetry API |

```bash
uv tool install "s1flow[eval]"
```

## コマンド { #the-commands }

```bash
s1flow init --task ticket-bug
# Fill in tasks/ticket-bug/task.py and add labeled data in the generated s1flow/ project.
s1flow cases check ticket-bug
s1flow run ticket-bug
s1flow report ticket-bug
s1flow adopt ticket-bug MODEL --reason "why this candidate" --json   # the new version is current
# open a pull request with the change: merging releases it
```

あるタスクで初めて `s1flow run` を実行すると、テスト用にケースの一部をホールドアウトし、`tasks/<task>/split.json` に書きます。`adopt` はこのファイルを読み、ファイルが無ければ動かないので、`task.py` と一緒にコミットしてください。このファイルを書くコマンドはほかにありません。あとから足したケースは ID のハッシュで振り分けられるので、ファイルの中身は変わりません。テスト用にホールドアウトできるほどラベル付きケースが無いときも、`run` はモデルに聞き、ファイルはあとの実行で書きます。

`s1flow init` は `s1flow/` プロジェクトを作るだけで、ほかには何もしません。`--skill` を付けると Agent Skill も書きます（[はじめる](get-started.md#add-the-skill-to-your-coding-agent)のとおり、プラグインとして入れることもできます）。

プロジェクトのラインナップは 4 つの Decision Model を比べ、どれも `OPENROUTER_API_KEY` という一つのキーで動きます（issue くらいの大きさの入力で、1,000 回あたり $0.01〜$0.05）。ケースは、GitHub の issue、アプリのログ、手元のラベルから集められます。GitHub からケースを取ってくる Skill の `scripts/github.py` を使うには、`gh` CLI を入れてサインインしておく必要があります。

`Task` は評価を定義します。データ、ラベルの読み方、問い、objective、制約、ケースの分割です。入力の準備にはアプリ自身の関数を使い回すか、アプリが実際に送った入力をリプレイしてください。`task.py` はアプリと一緒にデプロイしません。評価と本番の実行は、問いの型、答えの検証、判断のルールを共有します。指標は評価だけのものです。

## 候補を比べる { #compare-candidates }

`s1flow report` は、開発用のケースだけを使って、すべてのモデルと問いのバリアントを並べて見せます。バリアントは同じ問いの別の言い回しです。task.py に `variants={"strict": Boolean(instructions="...")}` のように書くと、`model/strict` という候補として動きます（Skill は間違いからバリアントを書きます: [フィードバックと改善](feedback.md#improve-the-question)）。

ターミナルには、タスクの objective の順に候補が並びます。上位で区別できない候補には `=` が付き、その中は task.py の `tiebreak` の順に（`tiebreak` が無ければ名前順に）並びます。どれを選ぶべきかの目印は付けません。`--json` を付けると、同じ候補 ID と数値で各候補のすべての指標が出るので、人や、人の代わりに動くエージェントが、自分の基準で選べます。テスト用のケースでの最終結果は、候補を採用したときにだけ出ます。

`adopt --reason` は選んだ理由を記録し、作業ツリーでその候補を `current` にします。この変更を含むプルリクエストがマージされると、本番に入ります（[ポリシー、証拠、リリース](policies.md)を参照）。

`s1flow report ticket-bug --out DIR` は `DIR/comparison.json` を保存します。これは、グラフ用のデータを含む、開発用の結果の完全なスナップショットです。問いのバリアントごとに `DIR/questions/<variant>.md` と `.json` も保存します。`s1flow report --from DIR/comparison.json` は、このスナップショットをオフラインで読み、採点や確認はし直しません。

スナップショットには、取得元と日付、プロバイダーとモデル、宣言した並列数と記録された並列数、レイテンシと費用の数字の出どころが残ります。数字の出どころは、請求額、定価、あるいは推定・混在・不明のどれかとして表示されます。不明な値は不明のままです。テキストと JSON のどちらの出力も、`--limit`、`--offset`、完全一致の `--candidate model[:version][/variant]` で絞り込めます。

## グラフ { #charts }

結果をブラウザで見るには、同梱のレンダラーでローカルのページを作ります。レンダラーは標準ライブラリだけで動きます。

```bash
python <skill>/scripts/charts.py comparison.json --out comparison.html
```

保存したスナップショットだけを読むので、評価用のツールを読み込むことも、モデルを呼ぶことも、採点し直すことも、採用することもありません。

ページは比べたすべての候補の表から始まります。列は、タスク自身の objective、問いの型が持つ指標（適合率・再現率・F1、macro-F1、MAE と QWK、mean IoU、正解率）、API の費用、p90 レイテンシです。スナップショットにあるそのほかの指標も、クリック一つで出せます。各セルには最悪の値から最良の値までのバーがあり、列ごとに最良の値が強調されます。列の見出しを押すと、その列で並び替わります。表示中のすべての指標でこの候補と同等以上の候補がほかに無いとき、その候補に ◆ が付きます。◆ は比べる価値のある候補を示すだけで、指標の重み付けはせず、どれを選ぶべきかの目印も付けません。

表の下には、任意の 2 つの指標を取ったトレードオフのグラフがあります。比べなかった候補とその理由、確率の曲線、測り方の詳細は折りたたんであります。グラフは出どころとサンプル数を付けて SVG か PNG でエクスポートできます。

スコアの問い（0 から L-1 までの段階）は段階の期待値で読み、共通の指標に加えて MAE（既定の objective）と QWK で測ります。ボックスの問いには、共通の指標と、確信度で絞り込んだときの曲線が出ます。対象が写っていない画像のケースは `False` でラベル付けし、モデルがボックスを返さなければ正解です（このとき IoU は 1、ラベルと答えの片方だけがボックスなら 0 と数えます）。

state から抽出する値（`Text`、`Number`、`Date`）は、ラベルと一致するか、`False`（値が無い）とラベル付けしたケースで何も抽出しなければ正解です。レポートは値があるケースと無いケースの正解率を分けて示します。答えの確信度はモデルの `p_null` と `confidence` から取ります。`RangeEstimate` は平均誤差（既定の objective は `MeanError()`）で測り、ラベルから `step` の半分以内なら正解と数えます（`step` が無ければ範囲の 1%）。p10〜p90 の区間が狭いほど確信度が高いと見なします。

`MultiChoice` は当てはまる選択肢のリスト（無ければ `[]`）でラベル付けし、選んだ選択肢がちょうどそれと一致すれば正解です。確率は選択肢の組み合わせ全体の確率で、選択肢ごとの「はい」か「いいえ」の確率を掛け合わせたものです。正解率は一つでも選択肢がずれたケースを不正解と数えますが、`OptionF1()` はすべてのケースのすべての選択肢を一つずつ数える objective です。`Boxes` のタスクは、写っている対象一つひとつのボックスのリスト（無ければ `[]`）でラベル付けし、どのボックスにも IoU の基準を満たす答えのボックスが一つずつあり、余った答えのボックスが無ければ正解です。`BoxF1()` はボックス単位で数え、レポートにはボックスの数のずれも加わります。ポリシーは、`Text`、`Number`、`Date`、`RangeEstimate`、`MultiChoice`、`Boxes` の 6 つの型も、ほかの型と同じように持てます。

はい／いいえの問いには適合率・再現率とキャリブレーションのグラフが加わります。選択の問いでは、モデルが実際の確率分布を返すとき、選ばれた答えの確率の曲線が出ます。プロバイダーが独自に返す確信度のスコアは別の信号として扱い、曲線に必要な信号が無いときは確率の曲線を描きません。

## しきい値と区間 { #thresholds-and-intervals }

はい／いいえの問い（と、正の選択肢がある選択の問い）では、ルールを決める objective（Accuracy、F1、ExpectedLoss、Recall、Loss、または `sets=` で指定する独自の指標）が、開発用の各フォールドの学習側でしきい値を選びます。レポートは、そのままの指標、しきい値を調整した交差検証の指標、ホールドアウトしたケースでの最終結果の 3 つを分けて示します。しきい値を調整することは、確率をキャリブレーションすることとは違います。

区間が重なる候補は、慎重を期して一つのグループにまとめます。このグループ分けは、候補が実用上も統計上も同等だと証明するものではありません。不明な測定値が設定した費用やレイテンシの上限を満たしたと数えられることはありません。

順位付けは、すべてのケースに答えがある候補だけを並べます。JSON の `candidates` には、証拠が違う候補や不完全な候補も残り、それぞれ何が足りないかが書かれます。

## 古い結果が使えなくなるとき { #when-old-results-stop-counting }

結果を使い回す前に、s1flow は実際に送った入力、問い、実際に使った接続、モデル ID、実装を確かめます。同じケース ID のまま入力を変えたり、エンドポイントやオプションを変えたりすると、前の応答は使い回されません。入力が変わっていなければ、モデルに聞き直さずにラベルを直せますが、それまでの評価結果とは合わなくなります。

並列数を変えると、それまでの性能の数字も使えなくなります。答えそのものは使い回せますが、以前に計測した時間を、新しい並列数で測ったかのようには出しません。測り直すには `run --fresh` を使います。

評価で使う独自のプロバイダーは、信頼された ModelSpec か TOML のエントリに `provider_revision` を書き、あなたの実装のコミットかパッケージのバージョンを示す必要があります。評価していない Client やポリシーには要りません。リビジョンを正しく保つのはあなたの責任です。`provider_revision` は署名ではなく、リモートのモデルの重みについては何も証明しません。
