# 考え方

s1flow の土台にある考えは一つです。**繰り返す判断は、Decision Model に任せる前に自分のデータで確かめ、モデルが確信している部分だけを任せる。** このページでは、この考えに要る言葉を、s1flow が回すループの順（ケースを集める、比べる、動かす、結果を戻す）に説明します。

## Decision Model { #decision-models }

自動化には分かれ道がたくさんあります。エージェントがそのまま実行するか人に確認するか、このチケットをどのチームに回すか、このメッセージは誰かを起こすほどのものか。どれも、似た入力に対して何度も繰り返す判断です。

Decision Model は、入力について型の決まった問い（はい／いいえ、いくつかの選択肢から一つ、など）に答えるモデルです。自由な文章ではなく、答えと確率を返します。Jev、Clef、d1、OpenAI の Decisions API などがこれに当たります（System One モデルと呼ぶプロバイダーもあります）。どの分かれ道にも置けるほど速くて安い一方で、どんな入力にも正しく答えるモデルはありません。どれくらい正しいかは、公開されたスコアではなく、あなたの入力で決まります。

## タスクとケース { #tasks-and-cases }

**タスク**は一つの判断です。問い、ラベル付きのケース、答えの測り方をまとめたもので、リポジトリの `s1flow/` フォルダの中の `tasks/<task>/task.py` に置きます。

**ケース**は、一つの入力（*state*。たとえば issue のタイトルと本文）とその正しい答え（*label*）の組です。ケースは、その判断がすでに行われている場所から集めます。GitHub の issue、アプリのログ、手元にあるラベル、モデルが確信できなかった判断への人の答えなどです。

タスクを初めて動かすとき、ケースの一部を**ホールドアウト**します。つまり、比較に使わずに取っておきます。比較には残りのケースだけを使うので、選んだ候補を最後に公正に試すときに、ホールドアウトしたケースを使えます。

## 候補と objective { #candidates-and-objectives }

**候補**とは、モデルと問いの聞き方（*問いのバリアント*、つまりプロンプト）の組です。s1flow はすべての候補に同じケースで答えさせ、それぞれをタスクの **objective**（目的の指標）で測ります。objective は、答えの使い道に合った測り方です。

正解率だけでは、たいてい足りません。正解率が同じ 2 つのモデルでも、一方がずっと多くの答えに確信を持っていれば、そちらのほうが多くの仕事を引き受けられます。objective は、この判断で「任せてよい」とは何かを決めます。

| 答えの使い道 | objective |
|---|---|
| 確信があれば実行し、残りは人に回す | 目標の正解率での **coverage**：その正解率を保ったまま、モデルが自分で答えられるケースの割合 |
| 対応が要るケースを、誤検知を出しすぎずに見つける | 誤検知の上限のもとでの**再現率** |
| 誤りの種類によってコストが違うとき、その釣り合いをとる | ケースあたりの**期待損失**（誤りの種類ごとにコストを決める） |
| 可能性の高いケースを先に並べる | **AUROC**：確率がケースをどれだけうまく並べるか |
| 数値として使うスコアを出す | **MAE**：スコアが人の付けた値からどれだけ離れているか |

objective は、その理由と一緒に `task.py` に書きます。決めるのは、その判断に責任を持つ人です。s1flow はその objective で測るだけで、代わりに選ぶことはありません。

## 確信度のしきい値 { #confidence-thresholds }

判断の一部だけを任せられるのは、Decision Model が確率を返すからです。objective が判断のルールを決めるものなら、s1flow は候補ごとに、そのルールをあなたのケースに合わせて決めます。coverage では、ルールは**最低確率**（min_probability）です。最低確率以上の答えは実行してよいほど確かで、残りは人に回します。再現率や期待損失では、ルールは正の答えの確率に対する**しきい値**です。誤検知を上限より少なく保つように、または誤りのコストが最も小さくなるように選びます。AUROC と MAE は確率やスコアをそのまま評価するので、ルールは決めません。

候補を採用するときは、ルールを合わせるのに使っていない入力でも成り立つかを、ホールドアウトしたケースで確かめます。

どの結果にも信頼区間が付きます。2 つの候補の区間が重なるときは、どちらかを良いと見なさず、区別できないものとして示します。比較は選ぶための材料で、順位表ではありません。

## ポリシー { #policies }

候補を選ぶと、`s1flow adopt` がホールドアウトしたケースでその候補を試し、**ポリシー**として保存します。ポリシーは、モデル、問い、しきい値を持つ一つの JSON ファイルです。アプリはこのファイルを読み込んで判断します。

**測ったものが、そのまま動きます。** ポリシーは、答えを変えるものをすべて固定します。モデルとそのバージョン、問い、入力の送り方、しきい値です。どれかを変えれば前の測定は当てはまらなくなるので、測り直して新しいバージョンとして保存します。保存したバージョンは書き換えないので、アプリが動かしたバージョンを、リリースしたときのまま読めます。

ポリシーを保存しても、変わるのは作業ツリーだけです。ポリシーを含むプルリクエストでレビューし、マージした時点でリリースになります。詳しくは[ポリシー、証拠、リリース](policies.md)を見てください。

## フィードバック { #feedback }

アプリが下す判断には、それぞれ**判断 ID** があります。確信できなかったケースを扱った人から、あるいはその後に起きたことから正解が分かったら、その ID に対して記録します。s1flow はそれを使って本番のトラフィックでポリシーを測り、正解の分かった判断を次の比較のための新しいケースにします。これでループが閉じます。モデルが確信できなかったところでケースが増え、次の比較はそのケースで測られます。

詳しくは[フィードバックと改善](feedback.md)を見てください。

## アプリに残るもの { #what-stays-in-your-app }

s1flow が持つのは、測定を変えるものと、正解を戻すのに要るものだけです。答えで何をするか、確信のない答えをどこに回すか、呼び出しが失敗したときのフォールバック、複数の判断の組み合わせ方は、あなたのコードかエージェントのフレームワークに残ります。s1flow は Python アプリの中か CLI として動き、自前のサーバーは持ちません。その理由とアプリにとっての意味は、[s1flow がアプリに任せること](app.md#what-s1flow-leaves-to-your-app)で説明しています。
